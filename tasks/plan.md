# Implementation Plan: Hilbras Studio Stabilization and Remediation

## Overview

This plan turns the repository audit into a staged remediation program. The goal is to make the existing Next.js application safe to operate and truthful about its capabilities before adding new features. The plan preserves the current Next.js App Router, PostgreSQL/Drizzle, Vercel, server-action, and provider-integration architecture; it does not require a rewrite.

**Planning assumption:** the immediate objective is remediation of the current product, not implementation of every feature advertised on the landing/pricing pages. Unsupported platform connectors remain connect-only or visibly marked unsupported until a separate connector project is approved.

## Success Criteria

The program is complete when:

- Composer cannot publish immediately while in schedule mode, and failed saves cannot be reported as successful.
- The UI, registry, documentation, and publisher capabilities agree.
- All model-call paths have bounded input/output/spend controls.
- Provider URLs cannot reach internal networks through redirects or DNS rebinding.
- Platform secrets are never returned to browser code.
- Scheduled publishing has timeout, lease, idempotency, and recovery behavior.
- Post terminal state and result URLs are server-authoritative.
- Account export/deletion behavior matches the published privacy policy.
- The repository has automated tests, CI, a passing lint gate, a typecheck script, and a passing production build.
- Dead code/dependencies are removed only after reference and migration checks.
- Each phase leaves the application buildable and deployable.

## Architecture Decisions

- **Risk first:** fix accidental publishing, credential exposure, SSRF, AI spend, and deletion semantics before refactoring.
- **Thin actions, server-owned invariants:** server actions remain the browser boundary, but authorization, validation, state transitions, and external side effects move into server-only services.
- **Capability-driven platform registry:** distinguish `connectable`, `publishable`, supported media, account selection, and token lifecycle instead of treating every registry entry as publishable.
- **Incremental database changes:** use additive migrations, backfills, verification, and only then contract/destructive changes.
- **No bulk rewrite:** split `publish.ts`, the data-access layer, and large client pages only after regression tests protect their current behavior.
- **External calls are bounded:** a shared server-side HTTP policy supplies timeouts, cancellation, response-size limits, and safe redirect handling.
- **No client-supplied terminal state:** publish results are generated by the server; clients may display them but cannot assert them.
- **Separate cleanup from behavior changes:** dead files/dependencies are removed in dedicated changes after the application is stable.

**Acceptance criteria:**

- [ ] `.env.local` is restricted to the owning user and unused local keys are identified.
- [ ] Rotation/reconnect steps are documented for session, encryption, database, AI, and webhook secrets.
- [ ] Tracked source/history is scanned for apparent credentials.

**Verification:**
- [ ] Secret-name-only inventory and permission check.

## Parallelization Opportunities

After Task 1 establishes tests and CI, these can proceed in parallel with separate ownership:

- Composer scheduling safety.
- Platform capability contract and UI gating.
- AI spend controls.
- Credential DTO/redaction.
- CSRF-safe cron endpoint.
- Documentation inventory (read-only preparation).

These must be coordinated or sequential:

- Database migrations, constraints, RLS, and deletion/export.
- Scheduler lease design and terminal-state service.
- OAuth provider contract and refresh-token work.
- Shared outbound HTTP policy, because SSRF, AI, publishing, and OAuth depend on it.
- Final dead-code removal, which should follow behavior stabilization.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Secret rotation invalidates encrypted records | High | Inventory encrypted rows and reconnect/re-encrypt deliberately; do not rotate blindly. |
| Scheduler changes duplicate or lose posts | High | Lease/attempt model, integration tests, explicit uncertain-side-effect policy. |
| Database constraints expose legacy bad data | High | Preflight queries, additive migration, repair script/runbook, then contract phase. |
| Provider API changes during OAuth work | Medium | Mock contract tests first; one provider/sandbox at a time; preserve compatibility adapters. |
| AI quota changes block legitimate users | Medium | Conservative defaults, configurable budgets, metrics, and staged rollout. |
| Public media URLs are externally relied upon | Medium | Check access logs and migrate to signed/expiring URLs before removal. |
| Documentation changes outpace code | Medium | Make capability matrix a tested source of truth. |
| Large refactors cause regressions | High | Extract behind tests one boundary at a time; no bulk rewrite. |
